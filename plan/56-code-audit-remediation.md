## A・優先修正

### ① 雲端舊檔升級逾時後，主按鈕應重試原請求

**修改位置**　升級卡派送 `confirmSaveUpgrade`，由 GameApp 交給持久層。持久層已有 `retryAttempt` 保存原快照與 requestId。修正放在持久層，讓主按鈕及頁尾的「重試保存」有一致結果。[升級卡](../src/ui/index.ts#L1234) · [命令入口](../src/app/app.ts#L572) · [確認與重試](../src/persistence/index.ts#L983)

1. 首次明確確認時，依讀到的 revision 建立一筆格式 9 升級快照。已送出且狀態仍為 `saving` 時，重複確認應合併為同一次操作。
2. 已確認升級且進入可重試的 `saveError` 時，交給現有 `retry()` 後直接返回。讓它選擇重送原寫入或重讀預覽 revision，避免再次建立 `pending`。格式不相容、權限失效及 revision 衝突繼續走各自的處理分支。
3. 以記憶體 CloudPort 模擬「主機已把 revision 7 存成 8，但第一次回應遺失」。測試從 App 派送第二次確認，讓它確實走到主按鈕使用的路徑。

**完成條件**　兩次呼叫的 data、格式、revision 和 requestId 完全一致；主機只增加一次 revision。等待 `flush()` 完成後共兩次寫入；成功後再按重試也沒有第三筆。沿用[持久層測試](../tests/persistence.test.ts)及[App 存檔整合案例](../tests/integration/app-persistence.test.ts)，選其中最貼近命令入口的一處補回歸案例。

### ② 雲端衝突出現後，遊戲時間應停止

1. 在 `worldIsFrozen` 把 `conflict` 與 `localConflict` 放進同一個凍結條件。`GameApp.update` 仍須先處理 UI 命令，才能在世界停止時接收 `useCloudVersion`。[凍結判斷](../src/app/state.ts#L113) · [命令與固定步進順序](../src/app/app.ts#L217)
2. 擴充現有的雲端衝突整合案例。在衝突已顯示、玩家尚未選擇時記下遊戲時間、HP 和位置，更新 100 毫秒，再按「載入雲端版本」。[既有案例](../tests/integration/app-persistence.test.ts#L141)

**完成條件**　等待期間遊戲時間、HP 和位置維持原值，沒有額外寫入。載入命令仍能讀取另一裝置的進度並回到角色列表；再次進入遊戲時，等待衝突的時間不會變成補跑的模擬步數。

### ③ 在打包前執行專案已有的檢查

將 Release 的專案步驟排為 `npm ci` → `npm run typecheck` → `npm run check:content` → `npm run build`。沿用同一個 job 的失敗處理，接回現有版本比對、固定工具校驗、pack 與 ZIP 驗證。[Release workflow](../.github/workflows/release.yml#L35) · [現有指令](../package.json#L10)

**完成條件**　在符合專案 engines 的 Node 24 環境分別執行兩項檢查，並核對任一指令非零退出時，後續 build 與發布步驟會中止。這項可從指令結果和 workflow 順序驗收，無須建立測試用 Release。

## B・玩家可見的邊界狀況

### ⑥ 預覽升級成功後解除升級卡

**相依**　排在①之後，沿用同一套重試入口。預覽的 `saveProgress()` 成功也回傳 null，因此結束升級的依據是後續 `loadProgress()` 讀到了甚麼。[預覽回讀](../src/persistence/index.ts#L862) · [GameApp 狀態通知](../src/app/app.ts#L458)

1. 在已確認的預覽升級回讀分支，核對當前工作階段、有效且已前進的 revision、預期寫入格式，以及資料能通過現有 profile 驗證。普通預覽保存繼續使用既有的回讀流程。
2. 驗證成功才清除持久層的升級狀態，並讓 GameApp 同步清除卡片。將「這次升級已完成」明確帶給 App，避免把每一次 `previewOnly` 通知都當作升級成功。畫面顯示「預覽暫存」。
3. 回讀逾時時保留原升級狀態；再次確認只重讀。回傳 null、仍為舊格式或工作階段已更換時，該回應不能解除升級卡或覆蓋新工作階段。

**完成條件**　用格式 8 預覽檔開始，模擬保存後回讀格式 9，原角色可選取並繼續遊玩。另以「寫入成功、第一次回讀逾時」驗證一次寫入即足夠。沿用[預覽回讀測試](../tests/persistence.test.ts#L470)，再從 App 快照檢查 `saveUpgrade` 和 `saveStatus`。

### ⑧ 讓舊長名稱可以完整輸入刪除確認

在角色管理表單把新名稱與確認欄的長度設定分開。新建／改名仍使用現行 16 字元規則；刪除確認與永久清除確認的 `maxLength` 使用該角色保存名稱的 `.length`。維持指令端的完整字串比對，載入舊檔時保留原名稱。[表單](../src/ui/roster-manager.ts#L18) · [刪除與清除指令](../src/persistence/profile-actions.ts#L28)

**完成條件**　用既有 24 字元名稱 fixture，確認兩種確認欄都容得下全名。用測試資料驗證完整相符才接受，少一字會拒絕，改名欄仍限制 16 字元。檢查表單屬性即可判斷輸入上限。[長名稱 fixture](../tests/fixtures/full-character-profile.ts#L23)

### ⑨ 切換音樂時釋放晚到的舊曲解碼結果

保留目前下載去重及淡出機制。在 `startDesiredMusic` 等待所有圖層解碼後，若原曲目已不是目前目標，讓既有 `evictMusic()` 依最新目標及仍在播放／淡出的圖層清理快取。特別核對 A → B → A 的快速切換，讓重新選回的 A 可用。[載入與驅逐](../src/audio/audio-controller.ts#L194) · [切曲完成分支](../src/audio/audio-controller.ts#L263)

**完成條件**　使用可控制解碼完成順序的假音訊介面。先選 A 再選 B，讓 B 先播放、A 後完成。B 應持續播放；此後重新選取已被清掉的 A 時，應觀察到新的載入。此案例可透過下載及播放次數驗證，毋須為測試公開內部快取。[既有音訊測試](../tests/audio-fallback.test.ts#L80)

## C・鏡頭與逐幀工作

### ④ 把相機設定放回切圖、換目標及調整尺寸的時機

1. 地圖載入成功時已有 `stopFollow`、bounds 和死區設定。在新地圖第一份有效快照中，先把玩家 sprite 放到新出生點，再呼叫一次 `startFollow`，採用現有的 0.12 插值與 200 × 120 死區。重新使用同一個玩家 sprite 時也要處理換圖或角色切換的首次定位。[載圖完成](../src/render/index.ts#L1554)
2. 移走畫幀中兩次 `startFollow` 及重複的相機設定。沿用相機跟隨事件更新視差；尺寸改變時更新 viewport、zoom 與背景尺寸。首次載入的背景仍需初始化，即使新舊地圖的 viewport 尺寸相同。[繪圖](../src/render/index.ts#L1155) · [相機更新](../src/render/index.ts#L1499) · [場景 resize](../src/app/scenes.ts#L152)

**完成條件**　固定尺寸下，連續跑動及跳躍不會重新啟動追蹤；地圖兩端受邊界限制，轉圖首幀定位正確，改變 iframe 尺寸後視差與畫布仍對齊。此項直接影響手感，適合一次短程無頭實玩，以轉圖前後的截圖確認首幀，搭配相機位置或呼叫計數確認連續幀；靜態截圖本身無法證明平滑度。

### ⑤ 先移除一般遊玩時的完整 profile 序列化，再決定是否共用任務視圖

**第一步可獨立交付。** 在 `renderScreen` 建立比對用資料時，只有需要讀取角色欄、角色資料或倉庫的畫面才納入 `profile`。保留各畫面實際使用的狀態，例如衝突、升級、載圖、選角忙碌和錯誤訊息。確認標題畫面的改名及倉庫轉移仍會觸發更新。[畫面比對](../src/ui/index.ts#L1139) · [角色管理整合案例](../tests/integration/profile-management.test.ts)

**第二步依量測決定。** 在相同角色、地圖與固定步數下，記錄 DOM 與世界渲染建立任務視圖的次數及耗時。若重複成本值得處理，優先讓兩個消費端共用同一份遊戲狀態衍生的結果。只在存檔狀態與職業化 catalog 都相同時重用；接任務、領獎、裝備／背包變化、轉職與切換角色都必須取得新結果。[UI 快照](../src/app/state.ts#L119) · [世界快照](../src/app/gameplay.ts#L574)

**完成條件**　多角色高進度 fixture 在一般遊玩時，畫面比對對完整角色列表的序列化次數為零；返回標題後仍能看到最新角色與倉庫。若實作任務共用，再確認同一快照只計算一遍，任務日誌、追蹤和 NPC 標記同時反映變更。若量測不支持第二步，記錄結果即可收束此項。保留[每個固定步進一次通知的既有契約](../tests/integration/app-step-notifications.test.ts#L16)。

## 實作與驗證結果

- **A（①②③）** 記憶體雲端主機先將 revision 7 寫成 8，再模擬首次回應遺失。App 再次確認會送出完整相同的請求，總寫入次數為兩次，主機 revision 仍為 8。衝突等待 100 毫秒期間，遊戲時間、HP、位置和寫入次數保持原值，載入雲端版本後可重新選角。Release job 依序執行 `npm ci`、`npm run typecheck`、`npm run check:content`、`npm run build`，任一步驟失敗即停止。
- **B（⑥⑧⑨）** 格式 8 預覽檔在讀回較新的有效格式 9 存檔後可選角。讀取逾時、空值、舊格式、舊 revision 或無效資料都保留升級卡，後續確認只重讀。完整的 24 字元名稱可通過刪除及永久清除的確認，少一字會被拒絕，改名仍限制 16 字元。受控解碼測試確認晚到的舊曲會釋放，快速切回尚在解碼的曲目可沿用同一次下載。
- **C（④）** 本機無頭 Chrome 使用測試角色從晨光營地跑跳並經傳送門進入木葉鎮。相機分別在 `(150, 600)`、`(100, 600)` 啟動跟隨，總計兩次。營地記錄 604 幀，水平可視左緣在 0–480 之間移動，兩端均到達。iframe 由 1280 × 720 改為 960 × 600 後，畫布的顯示尺寸為 960 × 540，畫面及背景對齊。[營地](../output/playwright/plan56-camera/camp-before.jpg) · [縮放後的木葉鎮](../output/playwright/plan56-camera/town-after-resize.jpg)
- **C（⑤）** 同一輪觀察到 659 次遊玩畫面比對，沒有序列化完整角色清單。標題畫面仍序列化角色資料，App 整合案例涵蓋改名及倉庫轉移後的進度。以高進度角色在同一張地圖上量測 1,500 個固定步進，兩端各建立 33,000 個任務視圖。DOM 端耗時約 6.15 毫秒，世界端約 5.40 毫秒，每步的重複工作約 0.004 毫秒，因此保留兩端各自計算。
- **D（⑦⑩）** 四個首領共用同一判斷，職業面板、SP 規則及存檔驗證使用各職業的可學技能名單。移除未讀取欄位與成功轉圖的重複賦值。相關案例涵蓋四職業各五個可學技能、舊檔技能等級、傳送、復活及首領重試。
- **本機檢查** 使用 Node 24.22.3，`typecheck`、`check:content`、`build` 通過，12 個相關測試檔共 143 項通過。無頭實玩使用同來源本機 iframe 及測試資料。正式 Playroom 預覽、雙裝置帳號驗收、完整回歸與 Release ZIP 驗證留待發布階段。此版尚未發布。
