## 1. 目標與執行順序

目標是在實際遊玩尺寸下，讓角色、裝備、近景、文字與特效呈現一致的清晰度，並維持移動時的穩定輪廓及合理載入成本。

建議順序：

1. P0：確認縮放／取樣／世界文字是否損失既有素材細節。
2. P1：主角動作精修與低密度裝備升級。
3. P1：近景平台、梯子、傳送門等常見物件升級。
4. P1：重擊特效及 UI 插畫縮放規則整理。
5. P2：中景與背景的層次、接縫及局部細節。
6. 各批完成時檢查成本；第一批結束後做一次有界的整合驗收。

第一個可交付批次只涵蓋晨光營地、布衣主角及代表性攻擊。先取得「已接進遊戲的前後對照」，再按同一規格擴展到其他裝束和區域。

## 3. 統一畫質標準

### 顯示標準

- 主要驗收為 1920×1080 桌面遊戲區、100% 頁面縮放；另檢查 1280×720 的縮小效果。
- 首批不更改角色顯示尺寸、相機視野或戰鬥判定。
- 高 DPI 與一般 DPI 分開記錄。CSS 尺寸、畫布實際尺寸和裝置像素比都寫入證據，不能只以「1080p」代稱。
- 4K／高 DPI 全螢幕若仍有額外需求，後續才評估 1440p 上限的高畫質選項；其效能與清晰度獨立驗收，不宣稱等同原生 4K。

### 美術標準

- 延續失序司鐘者的清楚輪廓、明確體積、材質分區和乾淨透明邊；各角色保留自己的外貌及配色。
- 主角正常大小即可辨認頭髮、臉、上衣、手、鞋與武器；不以極度放大的預覽圖作主要通過依據。
- 同一角色的臉型、頭身比例、裝束標誌、光源方向在連續影格中一致。
- 前景、角色、遠景有清楚視覺層次；遠景可以較柔和，互動物及可站立邊緣須清楚。
- 透明邊在明、暗兩種背景上均沒有明顯彩邊、白邊、黑底殘留或掉色；只檢查真正需要的局部裁圖。

### 像素密度標準

- 優先處理素材像素不足、或有效身形只佔圖片小部分的資產。
- 在 1080 畫布、960 邏輯視野的現有設定下，重要前景與角色通常以至少 2 個來源像素對應 1 個邏輯單位作起點；是否採用仍以遊戲內觀感決定。
- 不統一把所有圖集加倍。主角每套圖集目前解碼基本量約 9 MiB，若寬高均加倍會變成約 36 MiB；三套合計約 27→108 MiB，尚未計入其他副本。
- 低解析圖單純放大不列為細節升級；有高解析原稿就重新匯出，缺細節才重製。

## 4. P0：找出呈現過程的細節損失

工作量：小至中。依賴：現有素材即可。

工作項目：

1. 使用晨光營地既有截圖作基線，記錄 Canvas、CSS 顯示框、相機倍率與 DPR。
2. 建立一組代表性比較：布衣主角、森芽、斜向劍刃、平台上緣及 NPC 名字。
3. 比較現有取樣與適度平滑的效果，兼看靜止和移動。先確認 `antialias`、Canvas 圖像取樣及 CSS 圖像縮放各自影響哪一層。
4. 檢查小數縮放及相機跟隨時的輪廓跳動。相機目前已有 `startFollow(..., true, ...)` 的取整，先量測再改，不重複加入互相牴觸的取整。
5. 為世界名稱、傳送門文字和傷害數字試用對應相機放大倍率的文字貼圖解像度，保留目前邏輯字級與位置。
6. 高 DPI 只有在像素對照證明畫布尺寸不足時才進入品質選項設計；首批仍以 1080 畫布為主。

注意：世界使用 Canvas，全域取樣開關可能同時影響地形與角色。若某設定改善臉部卻明顯損害地形，就保留現狀並回到素材匯出處理。不要在每個物件繪製時任意切換共用 context 狀態。

涉及檔案：`src/main.ts`、`src/render/index.ts`；只有必要時修改 `src/render/geometry.ts`、`parallax.ts`。

交付：一份取樣比較、採用設定及原因；世界文字的正常大小局部對照。

驗收：人物細線與文字可讀性改善；相機視野、背景位置及右側物件裁切正確；移動不新增明顯抖動。若比較沒有可見收益，結束此項調參並移到 P1。

## 5. P1：主角動作與裝備精修

工作量：中至大。依賴：P0 已固定呈現設定。

先完成布衣裝束的小批樣本，再套用輕革甲及鐵環甲：

1. 對照待機、行走、跳躍和攻擊的完整連續影格，找出臉型變化、髮型跳動、手部與鞋子缺口。
2. 逐項修正有問題的姿勢。只有原稿本身不足時才使用 ImageGen 編修；不重新生成已達標的整套動畫。
3. 第一批檢查右向／左向與揮劍中段；之後覆蓋攀爬、受傷、死亡和增益狀態。
4. 將兩把 64×64 武器升級至至少能支援現有 1080 顯示的版本。可先採 128×128 原生細節稿；需要更精細邊緣才採 256×256。
5. 優先核對握點、旋轉、翻面後的劍柄與手部位置；帽子先檢查貼合，不因尺寸已大而重新畫。
6. NPC／普通怪物按遊玩中實際差距排序。首輪比較森芽、商人及一隻常見怪物，通過後才決定新增重製清單。

素材交付要求：

- 新原稿、參考圖、完整 prompt、來源與匯出報告保存在 `art-source/`。
- 使用版本化 runtime 檔名，Manifest 保留穩定的資產 key，方便逐項替換及還原。
- 保留動畫狀態、影格順序與時序；腳底、頭部、手部錨點均對照原本邏輯座標。
- 不從其他遊戲擷取素材。

涉及檔案：角色／裝備 PNG、`public/assets/actors/manifest.json`、現有 clarity 匯出工具。只有錨點證據需要時才改錨點資料或 renderer。

驗收：在正常大小可看出輪廓與材質提升；連續播放不換臉、不忽大忽小；待機腳底相對原定位偏差控制在 0.5 邏輯 px 內，其他姿勢以原動畫的預期位移為準；左右向裝備均貼合，攻擊範圍與時機保持一致。

## 6. P1：近景地形與互動物

工作量：中。依賴：P0 的取樣與美術標準。

優先順序及建議起始規格：

| 資產 | 現在 | 建議首版素材尺寸 | 保留的邏輯尺寸 |
| --- | --- | --- | --- |
| 平台 | 128×32 | 256×64 | 128×32 |
| 梯子 | 32×128 | 64×256 | 32×128 |
| 傳送門 | 64×96 | 128×192 | 64×96 |
| 營地牌 | 96×128 | 192×256 | 96×128 |
| 礦坑門 | 128×160 | 256×320 | 128×160 |
| 祭壇 | 112×96 | 224×192 | 112×96 |

先完成營地的平台、梯子及傳送門。重點是材質邊界、可站立上緣、木板／石塊結構與乾淨透明邊。

平台須檢查水平接縫、兩端、重複節奏及角色站立腳底。斜坡與基礎地面只在實際拼接存在問題時一起處理，不把已有足夠密度的地面重新製作列為前置。

涉及檔案：`public/assets/environment/manifest.json`、版本化 PNG、必要的環境匯出來源。碰撞地形資料維持原有規則。

驗收：1080 正常大小的前景質感能與角色相配；拼接沒有明顯裂縫／亮線；平台高度、梯子攀爬路徑與傳送門操作位置一致。

## 7. P1：重擊特效及 UI 圖像

工作量：中。可在角色及近景試作通過後接續。

重擊特效：

- 先將目前 128px 每格的重擊效果做成 256px 細節樣本，以清楚的刀光走向、命中核心及乾淨半透明邊為重點。
- 不先更改技能時序或傷害；如重製影格，對齊原本發動、命中與收尾時間。
- 橫掃／命中等已有 512px 每格，先調整視覺遮擋和色階，沒有具體問題就沿用。
- 不用強烈發光掩蓋角色或地形；敵人輪廓、血條與攻擊預警須可辨。

UI 圖像：

- 區分高解析插畫、真正像素素材及 DOM 文字；針對選單、頭像、快捷列圖示整理 `image-rendering` 的繼承與覆蓋。
- 六個選單圖示已有 256px，優先檢查瀏覽器縮小效果，不加入同樣用途的更大素材。
- 保留目前 B 版位置、底部三組間距、羊皮紙按鈕、任務收合及鍵盤焦點行為。
- 文字保留 DOM 文字；不烘焙成圖片。羊皮紙邊框繼續使用可伸縮分區，避免把裝飾角拉變形。

涉及檔案：`public/assets/interface/manifest.json`、特效 PNG、`src/ui/journal.css`、`control-art.css`、`forest-hud.css` 及有具體需要的面板樣式。

驗收：技能播放流暢、命中可讀；頭像及選單縮小後細節乾淨；最新已確認的 UI 排列保持一致。

## 8. P2：背景與整體層次

工作量：中至大。依賴：前景樣本已確立風格。

1. 先區分遠景柔和的美術選擇與素材不足造成的模糊；天空和雲通常不需要與武器相同的銳利度。
2. 針對中景樹幹、建築及近距離枝葉檢查放大後細節、重複接縫與視差穩定性。
3. 有原始大圖的背景先重新匯出；需要新增細節的部分再製作，保留可平鋪邊緣和各層透明關係。
4. 目前多數背景層高度為 540px；是否提升到 1080px 須按實際畫面需求決定，不能把所有主題一次加倍當作預設工作。
5. 先完成營地主題，再選一個較暗的礦區或遺跡驗證角色分離度；雪地、沙地按相同原則逐區處理。

涉及檔案：背景 PNG 與 environment Manifest。只有新增的視差問題才改 `parallax.ts`，保留 beta.59 已修復的縮放原點及可見範圍計算。

驗收：前後景有層次；角色與敵人容易辨識；橫向移動沒有明顯接縫、跳相或缺口。

## 9. 成本控制、驗收與停止條件

### 資產與執行成本

本輪盤點三份主要 Manifest 的圖片合計約 48.6 MiB；按寬×高×4 計算的基本 RGBA 解碼量合計約 309.5 MiB。這是全部映射的靜態估計，並非實際同時載入量或瀏覽器記憶體峰值；尚未包含額外副本、文字、UI 及其他資源。

- 每批記錄素材檔案大小、有效身形比例及解碼量變化。
- 先檢查哪些素材真的被該場景載入及保留，再決定是否需要延後載入或釋放；不為美術小改提前重構整個載入系統。
- 舊 runtime 素材先保留來源與回退能力；準備成品時再依引用清單決定包內資源，保留 repository 原稿。
- 同一環境比較固定的短段遊玩與載入時間。若新增畫質造成明顯掉幀、載入停頓或記憶體持續增加，先縮小該批資產或退回該項設定。
- 暫定效能警戒線為相同場景的 p95 幀時間惡化超過 10%；須先有可靠基線才採用。headless 測量只作相對觀察，不等同使用者桌面的實際 FPS。

### 最少必要檢查

| 變更類型 | 直接相關檢查 | 不預設執行 |
| --- | --- | --- |
| PNG／Manifest | 路徑、尺寸整除、透明、有效格、必要的錨點對照；接入成品時 content check 及 build | 全套單元測試、所有地圖遊玩 |
| 純 CSS 圖像縮放 | 選定一組正常大小的圖像與佈局核對；最後 build | 新增 CSS 單元測試、反覆截圖 |
| 相機／渲染幾何 | geometry／parallax 的相關既有測試，必要時新增覆蓋實際失敗的測例；typecheck、build | 與渲染無關的存檔／任務回歸 |
| 裝備錨點／動畫邏輯 | hero anchors／animation contract 的直接相關測例；typecheck、build | 為同一效果重複跑已過測例 |

第一批整合完成後進行一次 headless 實玩：

1. 1920×1080：晨光營地，布衣主角待機、左右行走、跳躍、攻擊；與森芽同畫面比較。
2. 1280×720：核對縮小後人物、UI 與世界文字。960×540 只核對必要的佈局／操作，不為每批重拍相同畫面。
3. 裝備批次另檢查兩把升級武器與左向握點；不為到達後期物件跑一遍完整世界流程，可使用隔離的測試流程並明確記錄方法，不能冒充正式玩家進度。
4. 背景批次只增加一個暗場景和短段移動；沒有必要不擴展成全世界回歸。
5. 檢查 console、pageerror、載入資源、無端裁切及該次相關操作，保存一份精簡結果。

瀏覽器固定 `headless:true`，依根 AGENTS 的已驗證啟動方式建立獨立 run／profile／port。正常暫停、指定 session close、停止自有 server 並保全證據；不開桌面視窗。

完整 PNG 留在工作區；審圖每次只載入必要的 1–2 張 JPEG 或局部裁圖，長邊 ≤1280、quality 60–75。1920 的細節判斷使用其原尺寸局部裁圖，不能只看縮小預覽。

相同產物、方法和尺寸已有通過證據時沿用；只有相關內容再次修改或出現新問題才重跑。環境失敗若與畫質變更無關，就記錄限制並停止擴大排查。

技術依據：

- [Phaser 3.90 Text／setResolution](https://docs.phaser.io/api-documentation/3.90.0/class/gameobjects-text#setresolution)：提高文字內部貼圖解像度會增加記憶體成本，應針對放大後的可讀性使用。
- [MDN devicePixelRatio](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)：裝置像素比、CSS 尺寸和畫布像素須分開記錄。
- [MDN Canvas imageSmoothingEnabled](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled)：放大取樣的平滑行為須依素材性質選擇，單一開關不能增加原稿細節。
