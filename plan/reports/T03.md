## 公開介面

`src/domain/combat/index.ts` 匯出：

```ts
createCombatState(): CombatState
tryAttack(
  state: CombatState,
  request: AttackRequest,
  actors: readonly CombatActor[],
  rules: RulesCatalog,
  nowMs: number,
  nextId: () => EntityId,
): Result<{ state: CombatState; attack: AttackInstance }>
stepCombat(
  state: CombatState,
  actors: readonly CombatActor[],
  rules: RulesCatalog,
  dtSeconds: number,
  nowMs: number,
  rng: RandomSource,
): CombatStep
```

### 行為邊界

- `tryAttack` 檢查來源存在且存活、技能存在且為 attack、技能陣營／rank、絕對冷卻時間、目前攻擊完整前搖／有效／後搖是否結束。basic 與敵招 rank 固定為 1，其餘玩家攻擊由 `skillRanks` 取得並限制到技能 `maxRank`。成功時快照腳底位置、朝向、rank、時間，建立空 `hitIds` 及下次可用時間；不讀 MP、不花 MP，也不改傳入 state。失敗以共用 `Result` 回傳，呼叫者可丟棄 state proposal。
- 攻擊矩形以建立時的 origin/facing 固定：向右 `[x,x+reach]`、向左 `[x-reach,x]`，垂直為 `[y-height,y]`；須與目標腳底座標的 body AABB 有正面積重疊。只可打異陣營且存活目標；按 origin 距離平方、再按 entity ID 字典序穩定排序。basic 最多 1 個，sweep 最多 3 個，其餘採 `SkillDef.targets`。
- `stepCombat` 以 `(nowMs - dtSeconds*1000, nowMs]` 與 `[startedAtMs+windupMs, activeEndMs)` 有交集為有效命中條件，因此固定 tick 跨過整個有效窗仍能判定。每段攻擊的 `hitIds` 保證同一目標至多命中一次；結束攻擊回收。來源缺失／死亡或技能定義失效的攻擊會移除並回報 `rejected`，避免留下幽靈攻擊；離圖時 app 仍應清除該世界的 CombatState。
- `damage = max(1, floor((attack * (multiplierBase + multiplierPerRank*(rank-1)) - defense*0.5) * (0.95 + 0.10*rng.next())))`。只對實際挑中的命中目標取 RNG。擊退依目標陣營用普通敵人 `(±120,-80)`、玩家 `(±140,-120)`，方向遠離快照 origin；x 重疊時採攻擊 facing，`knockbackImmune` 目標為 `(0,0)`。本包只產生 `Hit`，不直接修改 HP 或 movement。
- `CombatStep.started` 包含該 tick 開始的有效攻擊；`CombatStep.rejected` 用於 step 時清理的無效攻擊。`tryAttack` 的施放拒絕另由 `Result` 表示，app 可用 `{sourceId, code}` 記錄 UI／音畫事件。

## 接線示例

```ts
import { success } from '../contracts/index.js';

const skill = rulesCatalog.skills['heavy-strike'];
const attempt = tryAttack(combat, { sourceId: playerActor.id, skillId: skill.id }, actors, rulesCatalog, nowMs, nextId);
if (attempt.ok) {
  const mpPlan = skill.mpCost === 0
    ? success(player)
    : applyProgressAction(player, { type: 'spendMp', amount: skill.mpCost }, rulesCatalog);
  if (mpPlan.ok) {
    combat = attempt.value.state; // state 與 MP 一起提交；MP 失敗就丟棄 proposal
    player = mpPlan.value;
  }
} else {
  combatEvents.push({ sourceId: playerActor.id, code: attempt.code });
}

const step = stepCombat(combat, actorsAfterMovement, rulesCatalog, dtSeconds, nowMs, rng);
combat = step.state;
for (const hit of step.hits) applyHitInApp(hit); // player HP/T06 applyMonsterHit + T02 knockback velocity/until
// AI 在 windup 開始時用同一 tryAttack 路徑提交 enemy-melee／guardian-slam／guardian-wave。
```

app 可在 T14 tick 的「攻擊實例及命中」階段呼叫一次 `stepCombat`，再按 target faction 把玩家傷害交給 T04／app、怪物傷害交給 T06 `applyMonsterHit`，並套用 `movement.velocity` 及 `knockbackUntilMs = nowMs + 180`。T06 應在 AI windup 起始時送 `AttackRequest`；不要再另外計算第二套傷害矩形或命中時間。

## 主線戰鬥時間交叉估算（2026-10-18）

本輪重新讀取根 `AGENTS.md`、Playroom 最新 `game-agent-template.md` 及它列出的七份 `main` 文件（game-development、command-contracts、game.schema.json、game-release.yml、starter SDK、sdk-versioning、save-compatibility）；也重讀 `plan/01`、`07`、`08`、`09`、本 T03 task/report，並只讀核對 T01 規則、T05 任務表、實際 contracts、T04 起始／升級規則、T03 combat 與 T14 呼叫順序。適用要求是遵守本專案純 domain／固定時鐘／08 傷害公式，不改 T01 規則或 T05 目標；Playroom 成品、iframe 與發布驗收不由此戰鬥模型證明。沒有修改程式，因此沒有重跑測試。

下表將「高輸出」定義為每次升級將 AP 投 STR、轉職後 SP 優先升滿重斬、武器只用主線給的練習短劍／鐵製長劍／精鋼長劍；「普攻-only」是不投 AP、不學主動技能，武器也只用同一組主線武器。兩者都不計隨機裝備掉落、商店買武器、跑位、追怪、受傷／死亡、敵方攻擊、交任務或補給操作；假定每次玩家攻擊都處於 T03 的水平／垂直命中區，無須在攻擊之間移動。這是攻擊模型，不是完整路線實玩或通關時間。

攻擊值依 08 的 `3 + 2×STR + 武器攻擊`。高輸出在 q01 使用初始攻擊31；q03 起依等級下限與已分配 AP，攻擊值分別為129、159、189、241、281、321。重斬 rank 隨主線 SP 為 q03=1、q04=4、q05=7、q06–q08=10。高輸出的85次重斬總耗 MP 510；新角色起始的5瓶小藍水合計可供這個模型補足 MP（按 08 的最大 MP 上限使用），未把藥水操作算成額外攻擊等待。

普攻-only 的期望數使用 T03 的實際公式 `floor((attack − defense×0.5) × (0.95 + 0.10×rng))`，把 `rng` 視為均勻 `[0,1)` 後按各整數傷害機率計算擊殺攻擊數；合計期望為790.56。合約只保證 `rng.next()` 落在 `[0,1)`，沒有承諾機率分布，所以期望值是清楚標示的模型假設，實際 seeded run 會依種子不同；列出的範圍是公式端點造成的總攻擊數範圍。高輸出表中每個單體擊殺數在整個傷害倍率範圍內不變。

T03 的 `tryAttack` 在攻擊開始時設 `readyAt = start + cooldownMs`，並以 `windup + active + recovery` 鎖住下一次攻擊。玩家的 basic 為 550ms = 180+80+290，heavy-strike 為 650ms = 220+80+350，sweep 為 850ms = 260+100+490，因此主線這兩種攻擊的實際連續起手間隔正是表列冷卻；`stepCombat` 在 tick 跨入有效窗時至多命中每個目標一次，不會逐畫格重複扣血。

- 高輸出模型的冷卻加總（攻擊數×冷卻）是 58.55 秒；若每個任務戰鬥段連續出手、不計段間移動，首擊至最後一擊命中的下界為 55.60 秒（每段第一擊只等前搖）。因此 T01 報告的「約59秒」可解讀為把每次攻擊都乘完整冷卻的保守 cooldown budget，不是經過完整路線的實測耗時。
- 普攻-only 期望攻擊數的 cooldown 加總為 434.81 秒；七個戰鬥任務段首擊至最後命中的理想下界約 432.22 秒，即 7.20 分鐘。T05 報告的 815 次落在 746–822 次可能範圍內，但高於此均勻 RNG 模型的期望約24次；815次按同一冷卻與七段首擊前搖換算約7.43分鐘，和報告的7.2分鐘不完全一致。08 與 T03 沒有錯誤；T05 的815可視為粗略／偏保守數字，而其時間更接近本次重新計算的期望值。

結論：目前沒有證據顯示 T03 的攻擊鎖定、冷卻、傷害公式或有效窗有會實質改變上述攻擊量級的錯誤，故本輪不改 T03 程式，也不代 T01／T05 改資料。模型刻意略過所有跑圖及玩家操作時間；45–60 分鐘主線目標必須等整合遊戲可玩後以代表路線計時，不能由此處攻擊秒數驗收。
