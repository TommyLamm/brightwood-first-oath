## Delivered

- `tools/audio/generate-audio.mjs` deterministically writes the original compositions and `public/assets/audio/manifest.json`. Run `node tools/audio/generate-audio.mjs` to regenerate, or add `--check` to verify the existing output without rewriting it. Note sequences, tempo, waveforms, envelopes, and effects are kept in the script; no third-party audio or runtime service is used.
- `public/assets/audio/manifest.json` declares empty `images`/`animations` and sixteen unique relative audio URLs. The three `theme-*` entries have `kind: music, loop: true`; all effects have `kind: sfx, loop: false`.
- `src/audio/index.ts` exports `createAudio(manifest: AssetManifest, settings: Settings): AudioController` from `src/audio/audio-controller.ts`, matching the existing T00 contract without changing contracts or app code. The controller lazily creates one AudioContext on `unlock()`, catches browser/fetch/decode failures and leaves play silent, retries on later unlock calls, does not restart same-key music, crossfades over 400 ms, suspends the context to preserve music position while paused, applies clamped master × channel gains, leaves saved volume values intact when muted, caps each SFX key at four voices while stopping the oldest, and stops/disconnects/closes resources on dispose.
- Generated PCM WAV size is 2,959,818 bytes total (about 2.82 MiB), within the 4 MiB internal audio budget.

## T14 connection guide

Use the existing API directly; no new app or main signature is needed. Create one controller from the loaded `audio` manifest and current Settings. Call `unlock()` from the first player gesture. Call `setSettings(settings)` after accepted settings changes and `setPaused(paused)` when the app pause state changes. Call `setMusic(key)` only when the effective music category changes: camp/town → `theme-town`; forest-edge, mushroom-wood, red-ridge, mine-gate → `theme-field`; active guardian arena → `theme-boss`. The controller already ignores a same-key music request.

Suggested event mapping; play only on successful state changes and consume each new VisualEvent ID once:

| App event | Audio key |
| --- | --- |
| first accepted player jump input | `jump` |
| accepted player attack instance | `attack` |
| new `VisualEvent.kind === 'hit'` | `hit` |
| player HP decreases from damage | `hurt` |
| new `VisualEvent.kind === 'pickup'` | `pickup` |
| successful potion `useItem` | `potion` |
| equipment changes after equip/unequip | `equip` |
| quest accept or claim succeeds | `quest` |
| player level increases | `levelup` |
| player activates and completes a world portal transition | `portal` |
| player first reaches dead state | `death` |
| guardian boss result first changes to defeated | `boss-win` |
| user activates a UI button | `ui-click` |

`VisualEvent` snapshots retain effects across frames, so T14 should keep a bounded set of consumed event IDs. The current `AudioController` API has no status callback; failures are swallowed at the audio boundary and produce silence without rejecting game commands. T16 can verify audible browser behavior and next-gesture retry.
